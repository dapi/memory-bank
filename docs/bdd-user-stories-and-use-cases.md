# Как связаны User Story, Use Case и BDD-сценарии

Use Case и BDD-сценарии могут и обычно должны существовать параллельно. Они
описывают одно поведение на разных уровнях детализации и имеют разные жизненные
циклы. Между ними часто находится User Story — единица планирования небольшой
части пользовательской ценности.

```text
Use Case
Устойчивый пользовательский сценарий
        ↓
User Stories
Небольшие поставляемые части сценария
        ↓
BDD rules и конкретные examples
Точное ожидаемое поведение
        ↓
Автоматизированные проверки
Подтверждение поведения реализации
```

Главное — не копировать один и тот же контракт между документами, а определить
ответственность каждого уровня.

## User Story: небольшая часть ценности

Правильный термин — **User Story**, а не Use Story.

User Story — небольшая единица продуктовой работы, приносящая пользователю
некоторую ценность:

```text
Как клиент,
я хочу вернуть купленный товар,
чтобы получить деньги за неподходящую покупку.
```

Популярный формат выглядит так:

```text
Как <роль>,
я хочу <результат>,
чтобы <получить ценность>.
```

Этот шаблон — только подсказка. User Story не должна превращаться в полную
спецификацию. В классической модели у истории есть три составляющие — Card,
Conversation и Confirmation:

- **Card** — краткое напоминание о требуемом результате;
- **Conversation** — обсуждение деталей между продуктом, разработчиками и
  тестировщиками;
- **Confirmation** — способ убедиться, что история реализована правильно.

User Story считается скорее обещанием провести разговор, чем исчерпывающим
описанием требований. Это подчёркивают [Agile Alliance][three-cs] и
[Mike Cohn][user-stories].

User Story отвечает на вопрос:

> Какую небольшую часть ценности мы хотим реализовать сейчас?

Она помогает управлять backlog, определять scope итерации, обсуждать приоритет
и договариваться, когда работа завершена. После реализации история может
потерять актуальность как planning artifact: её основная задача — провести
изменение через delivery.

## Use Case: устойчивая цель actor-а

Use Case описывает основные способы, которыми actor взаимодействует с системой
ради достижения определённой цели.

По определению Ивара Якобсона и Алистера Кобёрна, use case объединяет возможные
потоки использования системы для достижения цели конкретного пользователя. Его
основные элементы — система, primary actor, цель, основной успешный flow и
альтернативные flows. Подробнее это изложено в [Use-Case Foundation][uc-foundation].

Пример:

```text
UC-007: Возврат товара

Primary Actor:
Покупатель

Goal:
Вернуть товар и получить предусмотренную правилами компенсацию.

Trigger:
Покупатель инициирует возврат ранее приобретённого товара.

Preconditions:
- заказ существует;
- покупатель имеет право управлять заказом;
- товар допускает возврат.

Main Flow:
1. Покупатель выбирает товар.
2. Система получает причину возврата.
3. Система проверяет правила возврата.
4. Покупатель передаёт товар продавцу.
5. Система регистрирует возврат.
6. Покупатель получает компенсацию.

Alternatives:
- срок возврата истёк;
- товар повреждён;
- требуется проверка оператора;
- возврат денег невозможен исходным способом.
```

Use Case отвечает на вопрос:

> Как в целом actor достигает устойчивой цели с помощью системы?

В отличие от User Story, Use Case обычно не ограничен одной итерацией, может
охватывать несколько features и остаётся актуальным после завершения отдельных
delivery-задач. В Memory Bank именно такую роль выполняет project-level
`UC-*`, как определено в [Use Case Flow](../template/memory-bank/flows/use-case.md).

## BDD-сценарий: конкретный пример поведения

BDD-сценарий — конкретный пример поведения системы, иллюстрирующий определённое
бизнес-правило.

BDD не начинается с Gherkin. Сначала участники обсуждают правила и примеры,
устраняют неоднозначности, а затем превращают важные примеры в исполняемые
спецификации. Современный BDD-процесс включает три повторяющиеся практики:

1. **Discovery** — найти правила, примеры и неизвестные вопросы.
2. **Formulation** — записать согласованные примеры на языке предметной области.
3. **Automation** — связать примеры с автоматизированными проверками.

Это каноническая модель из [документации Cucumber][bdd]. Сам подход вырос из
идеи Дэна Норта рассматривать требования и тесты через ожидаемое поведение
системы: [Introducing BDD][dan-north].

Пример BDD-сценария:

```gherkin
Rule: Неповреждённый товар можно вернуть в течение 14 дней

Scenario: Возврат товара на четырнадцатый день

  Given покупатель получил товар 14 дней назад
  And товар не использовался и не повреждён
  When покупатель запрашивает возврат
  Then система принимает запрос
  And сообщает покупателю порядок передачи товара
```

Это не общее описание возврата, а один конкретный пример, проверяющий одно
правило на значимой границе. В Gherkin `Given` задаёт существенный контекст,
`When` — событие, а `Then` — наблюдаемый результат. Детальная семантика описана
в [Gherkin Reference][gherkin].

## Разница между артефактами

| Артефакт | Главный вопрос | Масштаб | Жизненный цикл |
| --- | --- | --- | --- |
| Use Case | Как actor достигает цели? | Устойчивый end-to-end flow | Живёт, пока система поддерживает сценарий |
| User Story | Какую ценную часть реализуем сейчас? | Небольшая delivery-единица | Обычно заканчивается после delivery |
| BDD-сценарий | Что произойдёт в конкретной ситуации? | Один пример одного правила | Может жить как исполняемая спецификация |

Между ними нет обязательного соответствия один к одному. Agile Alliance
отдельно отмечает, что User Story и Use Case не эквивалентны и не имеют
универсального взаимно-однозначного mapping. См. [User Stories][agile-stories].

Обычно:

- один Use Case реализуется несколькими User Stories;
- одна User Story содержит несколько acceptance rules;
- существенное правило иллюстрируется одним или несколькими BDD-сценариями;
- один BDD-сценарий может затрагивать несколько шагов Use Case.

## Пример совместного использования

Возьмём Use Case:

```text
UC-007: Покупатель возвращает товар
```

Он описывает весь устойчивый сценарий: запрос, проверку правил, передачу товара,
решение, компенсацию и альтернативные flows.

На первом этапе команда может реализовать только один slice:

```text
US-041

Как покупатель,
я хочу оформить возврат неповреждённого товара,
чтобы получить обратно уплаченную сумму.
```

Во время BDD Discovery команда находит правила:

```text
BR-01: товар можно вернуть не позднее 14 дней;
BR-02: товар не должен быть повреждён;
BR-03: сумма возвращается исходным способом оплаты.
```

Затем подбираются примеры:

```gherkin
Scenario: Возврат на тринадцатый день
  Given товар получен 13 дней назад
  And товар не повреждён
  When покупатель запрашивает возврат
  Then возврат принимается

Scenario: Возврат на четырнадцатый день
  Given товар получен 14 дней назад
  And товар не повреждён
  When покупатель запрашивает возврат
  Then возврат принимается

Scenario: Возврат после окончания срока
  Given товар получен 15 дней назад
  When покупатель запрашивает возврат
  Then возврат отклоняется
  And покупатель получает объяснение причины
```

Здесь каждый артефакт выполняет свою работу:

- `UC-007` сохраняет целостный сценарий возврата;
- `US-041` определяет текущий delivery slice;
- `BR-*` фиксируют правила;
- BDD-сценарии устраняют неоднозначность вокруг границы в 14 дней;
- автоматизированные проверки подтверждают реализацию.

## Как распределить ownership в Memory Bank

Чтобы артефакты жили параллельно без противоречий, каждому типу факта нужен
один canonical owner.

| Факт | Canonical owner |
| --- | --- |
| Actor, цель, trigger и end-to-end flow | `UC-*` |
| Scope конкретной поставки | feature `brief.md` |
| Обязательное feature-требование | `REQ-*` |
| Acceptance и отрицательные сценарии | `SC-*`, `NEG-*` |
| Derived BDD-представление | `FUC-*` или executable specification |
| Способ проверки | `CHK-*` |
| Результат проверки | `EVID-*` |
| Архитектурное решение | `design.md` или ADR |

BDD-сценарий должен ссылаться на правило или requirement, а не создавать
скрытое новое требование только внутри `.feature`-файла.

## Что переносить из BDD в Use Case

Полный BDD-сценарий обычно не нужно копировать в Use Case. В `UC-*` достаточно
зафиксировать основной flow, ожидаемые альтернативы, исключения, postconditions
и стабильные бизнес-правила. Конкретные данные и граничные примеры лучше держать
ближе к acceptance и проверкам.

Например, Use Case может содержать устойчивый факт:

```text
ALT-02: Если срок возврата превышен, система отклоняет запрос
и сообщает покупателю применимое правило.
```

BDD-слой конкретизирует границу:

```gherkin
Given прошло 14 дней
Then возврат разрешён

Given прошло 15 дней
Then возврат отклонён
```

Так Use Case остаётся читаемым и устойчивым, а BDD-сценарии — точными и
исполняемыми.

## Основные ошибки

### Превращать User Story в огромную спецификацию

User Story должна инициировать разговор и ограничивать delivery slice. Если в
неё помещён весь Use Case, ей становится трудно управлять.

### Переписывать Use Case целиком в Gherkin

BDD работает через конкретные примеры правил. Механический перевод каждого шага
Use Case в `Given/When/Then` создаёт длинные процедурные сценарии.

### Описывать интерфейс вместо поведения

Плохо:

```gherkin
When пользователь нажимает синюю кнопку
Then открывается modal с id "refund-dialog"
```

Лучше:

```gherkin
When покупатель запрашивает возврат
Then система сообщает условия передачи товара
```

### Считать BDD задачей тестировщиков

Главная ценность BDD возникает во время совместного Discovery до написания кода.
Gherkin, написанный тестировщиком после реализации, может быть полезным
автотестом, но почти не помогает сформировать общее понимание.

### Дублировать бизнес-правила

Если одно правило независимо записано в Use Case, User Story, Gherkin и тестовом
коде, документы неизбежно разойдутся. Нужно определить canonical owner и
использовать ссылки или стабильные идентификаторы.

## Практическая схема для Memory Bank

```text
UC-* описывает устойчивую цель и flow
    ↓
feature brief выбирает delivery slice
    ↓
REQ-* фиксируют правила
    ↓
SC-*/NEG-* задают acceptance
    ↓
BDD examples конкретизируют неоднозначные границы
    ↓
CHK-* определяют проверку
```

Use Case сохраняет целостное устойчивое поведение продукта. User Story выделяет
небольшой ценный кусок для ближайшей поставки. BDD превращает правила этого
куска в конкретные, однозначные и проверяемые примеры.

Поэтому параллельное существование этих артефактов не просто допустимо. При
ясном ownership оно даёт одновременно целостность требований, управляемый
delivery и проверяемое поведение.
